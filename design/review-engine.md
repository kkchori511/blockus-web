# 블로커스 엔진 코드 리뷰

검토 대상: `src/engine/` 전체. 제공된 사양을 기준으로 읽기 및 메모리 내 재현만 수행했다. 엔진·테스트·설정 파일은 변경하지 않았다. 아래는 재현된 문제만 우선순위 순으로 정리한 결과다. P1 이상 문제는 발견하지 못했다.

## 1. [P2] 소수 좌표를 허용해 요청한 위치와 실제 보드 기록이 달라짐

- **위치:** `src/engine/board.ts:40–45`, `src/engine/board.ts:68`, `src/engine/board.ts:152` (`src/engine/game.ts:179–181`에서 이 검사를 사용).
- **원인:** 경계 검사는 숫자의 범위만 확인하고 정수 여부를 확인하지 않는다. `at()`과 `applyPlacement()`는 `y * 20 + x`를 배열 인덱스로 사용하므로 소수 좌표도 이 식의 결과가 정수이면 정상 칸으로 취급된다. 모양 정규화 검사도 전체 좌표에 같은 소수 오프셋을 더한 경우 통과한다.
- **재현:** classic에서 파랑 `I1`을 `(0,0)`에 놓고 나머지 세 색을 패스한다. 파랑 `I2`를 `[(1,1),(2,1)]`에 놓고 다시 세 색을 패스한다. 이제 `canPlace(state, 'I3', [[3.5,1.975],[4.5,1.975],[5.5,1.975]])`가 **true**이고 `place()`도 성공한다. 실제 변경된 인덱스는 **43, 44, 45**, 즉 정수 좌표 `(3,2),(4,2),(5,2)`다. 로그에는 소수 좌표가 그대로 남는다.
- **영향:** 정수 격자에 속하지 않는 수를 수락하고, 보드와 배치 로그의 좌표가 불일치한다. 좌표를 기반으로 하는 미리보기·리플레이에서 다른 위치가 표시될 수 있다. 정상적인 정수 좌표만 전달하는 호출자는 영향을 받지 않는다.
- **수정 제안:** 배치 경계에서 모든 `x`, `y`에 `Number.isInteger()` 검사를 적용하고 범위와 점유 상태를 검사한다. 소수 좌표는 반올림해서 받아들이지 말고 거부한다. 위 재현에서 `canPlace()`가 false이고 `place()`가 예외를 던지며 입력 상태는 유지되는지 확인한다.

## 2. [P3] 배치 좌표 배열을 참조로 저장해 외부 변경으로 이력이 훼손됨

- **위치:** `src/engine/game.ts:192` 및 `src/engine/game.ts:122`.
- **원인:** `place()`가 호출자가 넘긴 `cells` 배열과 내부 좌표 튜플을 그대로 로그에 저장한다. 이후 상태 복제도 로그 배열만 복사하고 이벤트는 공유한다. `Shape`의 readonly 타입은 원래의 가변 배열을 통한 변경을 막지 못한다.
- **재현:** TypeScript에서 `const cells: [number, number][] = [[0,0],[1,0]]`를 만들고, 새 classic 게임에 `place(start, 'I2', cells)`를 호출한다. 호출 후 `cells[0][0] = 10`으로 변경하면 반환 상태의 첫 배치 로그가 `[[10,0],[1,0]]`으로 바뀌지만 보드에는 `(0,0),(1,0)`이 계속 채워져 있다. 이 이벤트를 공유하는 후속 상태의 로그도 함께 바뀐다.
- **영향:** 드래그용 좌표 버퍼를 재사용하는 호출자는 의도치 않게 이미 확정된 수의 이력을 변경할 수 있다. 저장·리플레이 데이터가 실제 보드와 달라진다. 현재 `undo()`는 로그가 아니라 스냅샷으로 보드를 복원하므로, 이 문제 자체가 보드 되돌리기를 망가뜨리지는 않는다.
- **수정 제안:** 이벤트 생성 시 `cells: cells.map(([x, y]) => [x, y] as const)`처럼 배열과 각 튜플을 함께 복사한다. 호출 후 원본 배열의 요소 변경·추가·삭제가 반환 상태 및 후속 상태의 로그에 영향을 주지 않는지 확인한다.

## 확인 범위와 추가 발견 여부

- **게임 진행:** 2·3·4인 × 세 모드 × 시드 5개, 총 **45판**을 끝까지 실행했다. 종료 시 모든 색의 `out`, 보드 점유 칸 수와 남은 조각 수의 일치, 2인 색 소유 및 3인 점수에서 초록 제외를 확인했다. allRandom의 자동 `blockedDraw` 패스는 **447회** 관찰했다.
- **공용 색:** 현재 구현은 초록의 배치 또는 패스로 그 차례가 끝날 때 담당자를 순환시킨다. 시뮬레이션 로그에서 0→1→2 순환을 확인했다. 패스한 담당자가 다음 초록 차례에도 계속 맡아야 한다는 추가 조건은 주어진 사양에 없으므로 오류로 분류하지 않았다.
- **되돌리기:** 중간 배치 및 최종 배치 이후 패스를 거쳐 되돌렸을 때 보드·남은 조각·탈락 상태·현재 지정 조각·공용 색 카운터·RNG·종료 상태가 배치 전으로 복원되고 `turnId`는 증가하는 것을 확인했다. 다음 배치가 이전 되돌리기 대상을 교체하는 코드도 확인했다.
- **세트·배치·점수:** 기본 dailySet **1,000개** 모두 중복 없이 16개·66~70칸이었다. 5개 진행 상태에서 21개 조각씩, 총 **105건**의 배치 탐색 결과를 보드 전체의 모든 좌표·방향을 직접 검사한 결과와 대조해 일치를 확인했다. 21개 조각 정의·시작 모서리·색 순서·남은 칸 감점·완주 보너스·마지막 단일칸 보너스에서 추가 오류는 발견하지 못했다.
- **시간 제한:** 엔진은 `passTurn()`과 타이머 재시작 식별자인 `turnId`를 제공하지만, 경과 시간 측정이나 자동 호출 스케줄러는 포함하지 않는다. 실제 15/30/60초 경과에 따른 자동 패스는 이번 엔진 검증으로 보장하지 않는다. 외부 타이머 구현을 전제로 하는 API 구조 자체를 버그로 분류하지 않았다.
- **성능:** 위 45판 실행에서 측정한 `place()`의 최대 소요 시간은 약 **2ms**였다. 해당 환경·입력 범위에서 보고할 만한 성능 문제는 재현하지 못했다. 기기 전반의 성능을 보장하는 벤치마크는 아니다.

검증은 `node --import tsx`의 표준 입력 스크립트와 assert로 수행했으며, 새 테스트 파일이나 빌드 산출물은 만들지 않았다. 기존 Vitest 테스트 파일은 읽어서 검토했고 테스트 러너로 실행하지 않았다.
